# 関連項目の保存済み状態と候補の取得基準

Issue #99。main `078f0ad`、390px、Mock、専用隔離DBで、保存済みの二つの項目のうち一つを別画面から削除し、元のノートで候補を再取得する操作を確認した。項目削除とその親マップ削除の双方で、チェック一つとサーバーの関連ID一つが一致しているのに未保存表示と移動警告が出た。ノートと人間の本文は保持されていた。

別画面で新しい項目Bを作成して関連付け、元の画面が最新文書の関連A+Bを明示確認した場合も検証した。古い候補にAしかない状態で単純に候補との交差を基準にすると、確認したBが表示されず、保存済みの選択を未保存と誤認する。

## 取得基準

DocumentNodes は、候補がどの document / workspace / 保存済みnodes / 確認version に対して取得されたかを保持する。同じ基準に対する成功した完全な候補一覧だけが、削除された関連項目を確認できる。その場合に選択と保存済み基準の両方から存在しない項目を除き、表示する関連と同じ基準でdirtyを比較する。

親から新しい保存済み状態が確認された場合、古い候補は新しい関連を消す証拠にならない。最新文書の関連とメタデータを表示し、未掲載の確認済み項目を候補に補い、現在の基準で候補GETを再実行する。再取得中も確認済みの関連は保存済みとして扱う。Layout effect のcontext refと各GETのactive guardで、新しい基準になった後の旧応答・旧エラーが選択を変更しないようにする。

候補GETが失敗した場合は既存候補・選択を維持し、削除を推測しない。人間が別の有効な項目をチェック/解除していれば、保存済みの有効な関連との差分と移動保護を維持する。候補再取得は読み取りのみで、関連PATCH・本文書き込みはしない。

## 検証

- `tests/e2e/association-deletion.spec.ts`: 項目/マップ削除×人間の未保存選択の有無の390pxの4ケース。本文の追記・保存、二つのマップの関連保存、Mock学習目標レビュー、別画面からの削除、再取得、本文不変、移動まで検証する。GET503と再取得でも本物の未保存選択を保持し、明示保存で確定する。自動PATCHがないことも検証する。
- `tests/e2e/association-confirmed-context.spec.ts`: 新規項目を別タブで作成・関連保存した後、元のタブの人間の本文保存が競合し、最新文書を明示確認・再試行する390pxの2ケース。古いキャッシュと遅い旧GETの双方を検証する。新しい候補GETを遅延させている間も確認済みA+Bを表示し、偽未保存や旧GETによるBの消失がなく、本文/名前が保持される。
- 既存の関連確認・応答喪失・同じIDの後の選択・独立した取得エラーの回帰も維持する。

候補は既存のworkspace内の全項目APIを使用する。保存済み基準が更新されたときの追加GETは読み取りだけで、関連や本文を自動確定しない。本文・名前の保存、AI、認証、デプロイは変更しない。
