# Issue #58 — Node切替時のDocument一覧と取得回復

## 再現

2026-10-04、修正前main `1e5bd99`、Node.js 24、PostgreSQL 17の専用DB、Review/Search Mockで確認。
Node A/Bにそれぞれ別のDocumentを関連付け、B向け一覧GETを保留してBを選択。
Node名がBであることとB向けGET到着を確認してから、AのDocumentリンクが消えることを期待したところ、5秒間1件残って失敗した。
取得失敗後にも旧一覧が残り、再取得ボタンがない。

## 修正

一覧部分のみをworkspaceId/nodeIdをキーにするコンポーネントに分離。
切替直後から一覧・読込状態・取得エラーが現在のNodeに属する。
読込中、空一覧、取得失敗を区別し、失敗時には同じスコープで再読み込みできる。
effect cleanupで旧レスポンスを無視する。作成フォームは再マウントせず入力を保持する。
DB・関連・Markdown・Reviewや認証を変更しない。

## 学習導線と既存作業の比較

最新mainの別の操作専用DBで、Map → OAuthの人間定義済み目標 → ノート作成 → 手入力の検証本文 → 通常Pasteの引用ダイアログ → 出典付き引用保存 → FULL Mock Review → 本文への移動 → 手入力の追記 → 保存 → Outdated表示 → Review Again → 関連Nodeへ戻る → ノートを再び開く、を実際に操作した。
目標、出典、保存した追記、異なるRevisionに固定された2回の完了履歴を確認。本文生成や自動修正機能は追加していない。Mockでの確認であり、実AI品質の評価ではない。

#39と元checkoutの未コミット差分は読み取りだけで比較した。
元変更は日本語ラベル/共通メニュー、ノート自動保存・閲覧/編集モード、四辺の接続ハンドル等。
元 `node-documents.tsx` の差分は表示ラベル3箇所のみで、一覧の状態管理は修正前mainと同一だった。
#39の全体的な共通UI整理は今回の小修正では完了扱いにしない。
自動保存の `NoteSession` はbaseHashだけを扱い、現mainで追加済みのbaseWriteId、引用Undo transaction、関連目標表示/contextVersionとの調整がまだ必要になると読み取れる。取り込み/上書きの判断や実行はしていない。

## 検証

ブラウザ回帰テストでBの遅延中にAリンクを非表示、作成フォーム入力保持、Bの取得失敗、Aへ切替後のエラー消去、Bの手動再取得、空Node、旧BレスポンスがAを上書きしないことを確認。
専用DB名の安全検証で最初のテスト起動は停止したため、操作用DBと別の `_e2e_test` DBを作成して再実行した。
追加テストのコールバック型チェック失敗も修正してから全チェックを再実行した。

`npm run check` 成功：lint/typecheck、unit 98件、専用DB integration 43件、build、browser 29件（10.5秒）。
取得回復後のNode B・Bだけのノート・入力保持をスクリーンショットで視覚確認。
既知のbuild chunkサイズ警告は継続している。
