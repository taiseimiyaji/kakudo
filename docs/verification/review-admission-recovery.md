# レビュー受付の結果が不明な場合の履歴確認

Issue #103。main `0766f7a`、390px、Mock・専用DBで、論理/学習目標レビューの最初のPOSTが実202で受け付けられ、完了した後に受付応答を中断した。画面は通常再送を可能にし、同じ保存版・種類でPOST2・履歴2になった。進行中レビューだけを拒否するサーバーの重複防止は、既に完了した受付の再送には適用されない。

5種類で共通する受付要求に、結果不明と既知拒否の区別を追加する。通信失敗、5xx、成功応答の読取/構造/対象文書・保存版・種類の不一致は結果不明として通常の開始を止める。既存の400/409の受付理由やその他の既知4xxは維持する。

履歴を明示GETし、受付時に確認済みだった履歴IDを除いた同じ保存版・種類の候補を表示する。候補は別画面の受付かもしれず、同じ要求の完了を証明するものとは扱わない。選んだ候補の詳細確認はGETだけで、追加POSTはしない。候補の状態が完了/失敗でも、閲覧では元の結果不明ロックを解除しない。通常の開始と「もう一度レビュー」は停止したまま、履歴確認後に重複の可能性を承認した場合だけ新しい開始を有効にする。承認そのものではPOSTしない。表示中の同じ候補を再度開いてもdetailの再取得versionを更新し、内容を読み直せる。

対象の保存版は受付時に固定する。後から人間が本文・名前を編集/保存しても、以前の保存版の受付候補を確認できる。本文・名前・資料・関連の入力には触れない。ノートから移動するときは結果不明の受付も移動保護の対象になる。承認して移動した場合、この画面の結果不明状態は保持されない。

scopeのオブジェクト identity とmount/attempt refで、古いPOSTと回復GETのsuccess/error/finallyを破棄する。scope変更時のref更新はlayout effectで行い、render中に変更しない。開始と履歴読取は同期refで重複操作を止める。対象文書をA→別画面→Aへ戻っても、前の訪問の遅いGETが新しい結果不明状態を変更しない。

最初の8ブラウザ回帰は修正前mainで全て期待失敗した。追加3件は、候補を開くと結果不明を解除していた旧head `e50fff1` で期待失敗した。別要求の候補を開いた後、了承0回でPOST2・同じ版/種類の履歴2になることも実測した。リクエスト境界の10単体は対象一致、対象不一致、構造欠落、通信/JSON/5xx、既知409の受付理由を検証する。サーバーAPI、本文生成、Finding状態更新は変更しない。

サーバーidempotencyや受付IDの永続的照合は追加しない。明示承認した追加開始は、遅れて完了した受付と重複する可能性がある。一般的なAPI期限は追加せず、回復GETに新しい期限も設けない。すべてMock/所有専用DB/一時Markdown保存先で検証し、実AIや実資料取得はしない。
