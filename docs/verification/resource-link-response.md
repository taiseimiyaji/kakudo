# 資料関連付け成功応答と未保存本文の保護（Issue #126）

main `8b335723bfb5b3c0d5d6a2ab3ad501b8115a230a` の限定レビューで、既存資料の関連付けPOST応答だけが検証なしに描画stateへ入ることを確認した。取得一覧の検証と待機/離脱保護は既に別の回帰で保証されているため、この未確認のPOST経路1件だけを追加検証した。

人間が本文・名前・別の資料フォーム入力を変更した後、関連付けを実DBへコミットしてから、HTTP 201のResource.titleだけをオブジェクトにした。ノート全体が `Something went wrong!` に切り替わり、Markdown本文のtextboxは0件になった。DBの本文・名前は保存済みの元の値、資料の関連は1件だった。Promiseのcatchでは、state反映後にReactのrenderで起こる例外を防げない。

関連付け応答のResourceを既存の `readResourceList` で検証し、その後で `added` へ渡す。生の通信型はunknownにして、Resource形式・対象workspace・URIエンコード可能IDの既存検証を利用する。不正値はstate更新前に既存の安全な失敗表示へ流す。

製品変更はResourcePanelの通信型/受け取り方の置換と、検証1行の追加だけ。通信・失敗表示・明示リトライの契約、共有schema、本文保存、見た目には変更がない。

追加ブラウザ1件は次を確認する。

- 実DBへ関連付けた後に不正201応答を返しても、未保存本文・名前・同じCodeMirror・Undo/Redo・資料選択・別フォーム入力が残る。
- 手動リトライ前の関連付けPOSTは1件。DBの本文・名前は未変更で、実際の関連付けは1件存在する。
- 既存の明示リトライだけで関連付けを確認し、関連の件数は1件のまま。別の資料フォーム入力は残る。
- 人間の本文と名前の明示保存が成功し、DBのGETで一致する。

製品buildと開発StrictModeで追加1件が成功。最終チェックはlint/typecheck/build、単体272件、統合64件、ブラウザ261件。既存parserの単体境界や一覧/離脱/待機のケースは重複追加していない。

Mock・所有する専用DB・一時Markdownと作成したIDだけを使用した。実AI通信、既存ユーザーデータ、元の未コミット変更、認証、本番環境には触れていない。この修正は描画への取り込み検証であり、新しい通信期限・結果不明回復フローは導入しない。ネイティブIME・物理障害・クラッシュ復旧は未検証。
