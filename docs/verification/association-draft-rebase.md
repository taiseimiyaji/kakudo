# 保存済み関連の基準更新と人間の未保存選択

Issue #101。PR #100後の実main `df88c16`、390px、Mock・専用DBで、別画面による関連追加A→A+Bと、保存済み項目削除A+B→Aの後、最新文書を明示確認すると、元画面の人間の未保存選択Cが消えた。本文・名前は残るが、CはDBにも保存されず、未保存表示が消えた。

DocumentNodesの保存済みID変更時の `setSelected(ids)` が原因。新しい保存済み基準を採用するとき、前の基準と現在の選択との差分（追加・解除）を新しい基準へ引き継ぐ。自分の関連書き込みの応答を失い、既存のID/writeId条件で確定を確認した場合は、送信済み集合を比較元にする。これにより送信後の選択変更を未保存として保持する。自分の書き込みが確定したという既存条件を緩めず、GETによる確認だけでPATCHを再送しない。

| 操作 | 期待する状態 | 検証 |
| --- | --- | --- |
| 別UIで関連B追加 / 保存済みB削除 → 最新文書確認 | 人間の追加C / 解除Aを保持し、未保存表示・離脱保護を継続 | 390pxの4回帰 |
| 自分の関連B追加 / 解除が確定 → 応答喪失 → Bを逆方向へ変更・C追加 → 明示確認 | 書き込み確定を表示し、その後のB・Cの選択を保持。PATCHは再送しない | 390pxの2回帰 |
| 本文・名前を保存再試行 → 関連を明示保存 | 本文保存だけでは関連の差分を確定しない。関連保存後だけDBを更新 | 外部変更4回帰に含む |
| 候補GETで削除を確認 / 古い候補や文書応答が後着 | PR #100の現在contextとread versionの保護を維持 | 既存回帰 |

`modules/editor/association-draft.ts` は前の基準に対する人間の追加/解除を新しい基準へ適用する。unitは他画面との独立変更、同じ追加を他画面でも保存、削除済みの変更なし項目を復活させないこと、確定した自分の送信後の逆方向変更を検証する。候補GETによる実在確認・削除の除去は従来の責務のまま。

修正前の6ブラウザ回帰は未保存表示消失、または送信後の逆方向選択消失で期待失敗した。外部追加は実際の競合、外部削除は文書確認UIを使うためPUTだけ既知500。manual-note-fixtureは自動保存intervalのみ遅延させる。DBは所有する専用DB、Markdownは一時保存先、AIはMockを使用する。
