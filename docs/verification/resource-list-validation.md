# 資料一覧の不正応答と未保存ノートの保護（Issue #122）

## 原因と修正

main `6e73a371f4dd45a4320d8b0d9a6d6390a2df0f95` で資料一覧GETを保留し、ノート本文・名前を変更してから HTTP 200 / `{ "resources": {} }` を返した。参考資料パネルを閉じていても、ノート全体が `Something went wrong!` に切り替わり、Markdown本文のtextboxが0件になった。隔離DBへのGETでは元の保存済み本文と名前が残り、未保存の入力は画面から失われた。

TypeScriptの通信戻り値型は実行時の検証ではない。不正な値をstateへ入れた後、一覧のrenderが失敗してルートのErrorBoundaryに到達していた。

`client/resource-list.ts` は一覧形式・各Resource・要求したworkspace・IDのURIエンコード可否を検証する。関連資料と登録済み資料の両方の検証が終わってから、`ResourcePanel` が一括で一覧を反映する。不正な一覧は既存の読み込み失敗へ流し、初回は空一覧と誤表示せず、再取得では取得済み一覧を保持する。安全な既存表示と明示的な再試行を利用する。

製品変更は上記2ファイルのみ。API契約、本文保存、関連付け操作、認証、見た目、依存関係には変更がない。

## 回帰確認

単体18件で空一覧・有効なResource・将来のenvelope追加項目・合法なUnicode/ASCII IDを許容し、非配列・不正な項目/URL/タイトル/種類/ID・異なるworkspace・一部だけ不正な一覧・URIエンコード不能IDを丸ごと拒否する。合法なIDは正規化せずそのまま返す。

ブラウザ6件は390px幅で、初回/再取得 × 非配列の関連資料/異なるworkspaceの登録済み資料/URIエンコード不能IDを含む関連資料を確認する。いずれも不正なHTTP 200を返す。

- 未保存本文・名前・資料フォーム入力が残り、同じCodeMirrorを維持する。
- 閉じた参考資料パネルを開くと既存の失敗表示になり、空一覧や診断文字列を表示しない。
- 再取得失敗でも取得済みの資料・選択候補・直前に実DBへ登録した資料が残る。
- 本文のUndo/Redo、明示的な一覧再試行、明示的な本文保存が成功する。保存後の本文・名前は隔離DBへGETして比較する。
- 検証失敗に伴う本文PUTは0件。明示的な保存で1件となり、追加の不正一覧GETを発生させない。

開発StrictModeでは最初のmount GETがcleanupでキャンセルされ、もう一度開始される。キャンセルがネットワークのinterceptionより先なら観測GETは1件、後なら2件となる。初回のみこの上限2件を許容し、製品buildと再取得は1件を要求する。失敗表示後に観測した件数を保持し、明示的な再試行後も不正GETが増えていないことを比較する。

追加レビューでは `id: "\uD800"` がJSONと一般の `resourceSchema` を通る一方、資料行の `encodeURIComponent(id)` がURIErrorを投げる経路を確認した。公開済みHEAD `55839dc9ac251bfcc64d28981ce0b5dd3c3309aa` のcheckoutで、reader直接回帰3件が拒否されず失敗し、初回/再取得の追加UI2件でもルートのErrorBoundaryを再現した。

一覧reader内で各IDをURIエンコードしてからstate反映へ進む最小修正を追加した。UUID/ASCIIへの限定やIDの置換を行わず、日本語と有効なsurrogate pairを含むIDは引き続き受理する。一般のshared schemaや他のAPI契約は変更していない。

最終チェック: lint、typecheck、単体272件、統合64件、build、ブラウザ251件。開発StrictModeの追加6件も成功。

## 環境と境界

Mock Provider、所有する専用DB、一時Markdown、制御したブラウザ時計のみを使用した。元の作業ディレクトリの未コミット45ファイル、既存ユーザーデータ、実AI通信、本番環境は対象にしていない。ネイティブMac IME、物理ディスク障害、クラッシュ復旧は未検証。

この修正は資料一覧GETの検証に限定する。既存資料を選択した状態・関連付け応答の待機中に離脱保護が働かない別の問題は実測済みで、次の改善候補として扱う。
