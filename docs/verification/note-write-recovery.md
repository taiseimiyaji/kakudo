# 本文保存・引用の待機と結果不明の回復

Issue #117。実main 5a5385dで、UIから作成して人間の本文を保存したノートのautosave PUT200と引用POST201を、実サーバーの確定後に保持した。制御browser時計45秒後も書込1、保存中、最新内容確認なしだった。引用ではキャンセルとEscapeも無効だった。応答解放後は正常保存・引用Undo/Redoが動いたため、期限と結果不明時の回復が不足していることを2経路で実測した。

## 修正

- 一つの文書が所有する `NoteWriter` のPUT・引用POSTに20秒期限を設ける。JSON読取、対象workspace/document、正規化された名前、更新write ID、本文hash、引用の決定的な挿入結果の検証も期限内に含める。期限・取消はrejectしてからabortし、遅い応答を採用しない。unmountで取消し、StrictModeのeffect再実行では新しい取消scopeを使う。
- 期限、通信喪失、5xx、壊れた成功応答を結果不明として扱う。NoteSessionのflight・holdと引用dialogのbusyを解放し、本文・名前・出典入力・Undoを保持する。自動保存、明示本文保存、引用再送、関連保存、削除を止める。引用はキャンセル／Escapeで編集へ戻れる。既知の4xx拒否の明示retryは維持する。
- 既存の最新内容確認GETにも既存 `readNote` の20秒期限と取消を適用する。GETは成否の証明ではなく、取得した本文と名前を表示する。現在の人間の入力で置き換える意図を明示確認した場合だけ、既存の基準確認で結果不明の保護を解除する。GETと確認は書込0、自動保存は停止したまま、明示保存だけが再開する。
- 関連項目は保存だけを止め、読取と未保存の選択編集を維持する。関連の削除確認で古い最新内容のGETを取り消し、本文・名前を保持する。確認後に別の人間が保存した場合は、既存baseHash/baseWriteId競合で明示保存も409となる。

一般API、server、Provider、認証、関連保存／削除の期限には変更なし。新しいpoller、自動再送、AIによる本文生成は追加しない。

## 検証

- 修正前の追加ブラウザ2件は期待どおり失敗。実PUT200／引用POST201の確定後に応答を保持し、結果不明と回復操作の欠如を確認した。
- 追加単体20件。JSON待機、期限直前／期限後、外部取消、閉じたscope、StrictMode再開、旧scope遅延、正常な本文／引用ACK、不正な成功内容、既知400/409と結果不明503、domainの再送・queued quote/context/delete保護を確認した。
- 追加ブラウザ8件。保存／引用期限、GETと意図確認の書込0、後の人間の本文・名前、引用出典とnative Undo/Redo、clean draftの結果不明、壊れた引用201、確認GETの期限と旧snapshot、確認後の外部保存409、文書切替取消、既知400の直接retryを確認した。関連の読取後も結果不明の保存は再開しない。
- 初回境界7件は6成功／1fixture失敗。次の文書の読取完了前に時計を45秒進めていたため、次文書の編集操作が表示されるまで待ち、7件成功。
- 初回全体はlintの未使用fixture変数を検出。その後228成功／6失敗で、従来の通信喪失・5xx後の直接再試行という前提を、GET後の明示確認に更新した。既存の本文／名前／資料／関連draft保持と再送数のassertionは維持した。
- 次の全体は233成功／2失敗。結果不明の保護が関連の読取操作まで無効にしていたため、書込の保護を分離した。旧GETは取消後にhandler完了を待ち、旧payload非表示と削除証明の順序検証を維持した。
- 最終lint/typecheck/build、単体240件、所有隔離DB統合60件、全ブラウザ235件成功。開発版StrictModeで保存／引用期限2件も成功。

Mock、所有隔離DB、一時Markdownのみ。期限検証は制御browser時計であり、実ネットワーク経過時間、native IME、実AIを検証したという主張はしない。元の未コミット作業とユーザーデータは保持する。
