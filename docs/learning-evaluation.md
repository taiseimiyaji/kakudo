# 学習体験の評価手順

PoCの機能受け入れと学習効果の検証を区別する。本書は仕様§47の5仮説を利用者と評価するための手順であり、学習効果を証明した結果ではない。

## 1セッション

1. 実施日、参加者ID、題材、事前知識、利用Provider / Modelを記録する。Mockは操作説明用に限り、学習効果の評価には使わない。
2. 参加者がNodeとLearning Objectivesを設定する。SeedのOAuthを使う場合は4目標の意味を本人が確認する。
3. 資料を読み、Node / Documentへ登録する。本人が自分の言葉でMarkdownを書く。必要な引用はSource URL付きで追加する。
4. 保存してReviewする。本人が指摘を読み、Evidenceを開き、該当箇所と主張を照合する。取得不能・根拠不足と誤りを区別できたか記録する。
5. 各Findingを本人が判断し、Resolve / Dismissの理由を聞く。修正が必要なら本人が書く。評価者やAIが修正文を与えない。
6. 保存・再Reviewし、対象Revisionが変わったことと、以前のレビューが残っていることを確認する。
7. ノートやAIを見ずに、本人のObjectivesを自分の言葉で説明してもらう。事前に用意した人間の評価基準で、正確性・理由・根拠への説明を記録する。後日同じ観点で再確認する。

記録対象は操作時間、迷った箇所、資料を開いた回数、Findingの判断理由、本人の修正、説明の評価。APIキーや不要な個人情報を記録しない。

## 仮説ごとの観察

| 仮説 | 比較・観察 | 成立を判断する前に確認すること |
| --- | --- | --- |
| 1：本文生成なしでもAIが役立つ | Review前後で本人が気づいた誤り・不足、役立った指摘、誤指摘を聞く | 指摘件数だけを改善と扱わない。本人が理由を理解したか |
| 2：自分で修正するサイクルが理解を深める | 事前・直後・後日の独力での説明を比較 | 題材と事前知識を揃える。通常のAI回答との比較は別条件として本人の同意を得て行い、Kakudoに生成機能を加えない |
| 3：MapとMarkdownの接続が役立つ | 次に学ぶNode、理解を記録したDocument、未達目標を本人に探してもらう | 探索時間に加え、関連を説明できるか |
| 4：Paste制限が本人の理解を促す | Quoteへ切り替えた理由、自分で書き直す際の思考、操作負担を聞く | 入力の不便さによる離脱も記録。貼り付け減少だけを理解向上と扱わない |
| 5：Fact Checkと資料管理が根拠へ戻す | Evidenceを開いたか、原文を確認して判断を変えたかを聞く | AI結果の無条件採用・誤指摘への追従が起きていないか |

最初は少人数の定性的な評価として扱う。参加者数・題材・順序の偏り、AI結果の変動を記載し、比較研究を行わない段階では優越性や因果効果を断定しない。

- 実施日 / 参加者ID / 題材 / 事前知識：
- Provider / Model / Review ID / Revision ID：
- 本人のObjectives：
- 参照資料と確認した箇所：
- Findingの判断と理由：
- 本人が修正した内容と、その理由：
- 独力での説明の評価（事前 / 直後 / 後日）：
- 操作で迷った箇所・中断・改善要望：
- 各仮説を支持した観察 / 反する観察 / 未確認：
